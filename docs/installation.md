# Installation Guide — Forge Control Plane + Beacon

> Fresh install from bare metal to a running panel. Base sources: `forge/install/install.sh` (782 lines) and `infra/compose.yml` (730 lines, 14 services).

## 1. Supported OS Matrix

`forge/install/install.sh:32` declares `SUPPORTED_OS` — this guide documents the primary tested matrix (Ubuntu 22.04/24.04, Debian 12) as required by the task.

| OS | Version | Arch | Status | Notes |
|---|---|---|---|---|
| **Ubuntu** | **24.04 LTS (Noble)** | amd64, arm64 | ✅ Supported (primary) | `install.sh` pre-flight detected via `/etc/os-release` |
| **Ubuntu** | **22.04 LTS (Jammy)** | amd64, arm64 | ✅ Supported | Same detection path |
| **Debian** | **12 (Bookworm)** | amd64, arm64 | ✅ Supported | Verified in `install.sh:185-221` `check_os` |
| CentOS | 7 / 8 / 9 | amd64 | ⚠️ Legacy — in `SUPPORTED_OS` array but not in task matrix | Will pass `check_os` but untested for Caddy/Beacon |
| Ubuntu | 20.04 LTS (Focal) | amd64 | 🔬 Untested | Bypasses check only with `--skip-checks` |
| Debian | 11 (Bullseye) | amd64 | 🔬 Untested | Same |
| macOS / Windows | 13+ / 10+ | amd64, arm64 | 🛠️ Development only | Use Docker Desktop; not for `install.sh` |

> `install.sh` checks `lsb_release`, `/etc/os-release`, and `/etc/redhat-release` (`check_os:185`). Unsupported OS aborts unless `--skip-checks` is passed.

Primary matrix for this guide: Ubuntu 22.04, Ubuntu 24.04, Debian 12 — all amd64/arm64, all verified in `install.sh` `check_os`.

## 5. Install Paths & Pre-flight

### Option A — Automated installer (`forge/install/install.sh`)

The installer is the fastest path for a single-host Forge deployment. It mirrors `infra/compose.yml` service topology but generates a standalone `/opt/gamepanel/docker-compose.yml`.

**Constants (`install.sh:16-20`):**
- `INSTALL_DIR=/opt/gamepanel`
- `DATA_DIR=/var/lib/gamepanel`
- `CONFIG_DIR=/etc/gamepanel`
- `LOG_DIR=/var/log/gamepanel`

**What it does (`main:746-779`):**
1. `parse_arguments` → flags `--unattended --skip-checks --force --verbose --fqdn --email` (passwords are never arguments — see below)
2. Pre-flight: `check_root` → `check_os` → `check_docker` → `check_docker_compose` → `check_resources` → `check_ports` → `check_existing_installation`
3. `gather_input` (interactive or unattended validation)
4. `create_directories` (750 for install/data/config, 755 for logs)
5. `generate_configuration` → `$CONFIG_DIR/.env` (FQDN, admin creds, DB, `DOCKER_REGISTRY=ghcr.io`, `APP_URL=https://$FQDN`)
6. `generate_docker_compose` → `$INSTALL_DIR/docker-compose.yml` (services: `api`→8080, `database` postgres:15-alpine→5432, `web`→3000, `proxy` nginx→80/443, network `gamepanel_network`)
7. `generate_nginx_config` → `$INSTALL_DIR/nginx.conf` (HTTP→HTTPS 301, TLS 1.2/1.3, proxy to `api:8080`/`web:3000`, `/ws/` upgrade)
8. `start_services` → `docker-compose pull` + `up -d`, 10s wait
9. `verify_installation` → `docker ps --filter name=gamepanel-*` ≥3, `curl /api/health` + `curl :3000`
10. `show_summary`

**Interactive:**

```bash
sudo ./forge/install/install.sh
# prompts: FQDN, admin email, admin password (confirm), DB password (confirm)
```

**Unattended:**

```bash
# Credentials come from the environment (or a hidden prompt when a TTY is
# attached). Passing them as arguments exposes them via ps(1)/procfs, shell
# history and CI logs, so --password/--db-password no longer exist.
sudo GAMEPANEL_ADMIN_PASSWORD='MySecurePass123' \
  GAMEPANEL_DB_PASSWORD='MyDBPass123' \
  ./forge/install/install.sh --unattended \
  --fqdn panel.example.com \
  --email admin@example.com
# Optional: --skip-checks --force --verbose
```

Post-install management (printed by `show_summary:732-736`):

```bash
cd /opt/gamepanel && docker compose up -d      # start (or docker-compose)
cd /opt/gamepanel && docker compose down       # stop
cd /opt/gamepanel && docker compose restart    # restart
cd /opt/gamepanel && docker compose logs -f    # logs
cd /opt/gamepanel && docker compose pull && docker compose up -d  # update
# Config: /etc/gamepanel/.env (chmod 600)  Logs: /var/log/gamepanel
```

> SSL: not auto-configured by this script (`show_summary:739` warns). Place certs in `$INSTALL_DIR/ssl/` (`fullchain.pem` + `privkey.pem`) or terminate TLS at host nginx/Caddy.

### Option B — Production Compose (recommended, `infra/`)

This is the verified multi-service stack (`infra/compose.yml` 14 services + `compose.production.yml` 10 overrides). Prefer it for monitoring, backups, and Beacon co-location.

## 6. Environment Setup

Do **not** hand-write secrets. Use `infra/gen-env.sh` (391 lines) which generates `infra/.env` + `.metrics-token` + `infra/secrets/*.secret`; Windows equivalent `infra/gen-env.ps1` (140 lines) generates `infra/.env` without `TAG`/Docker-secrets (see drift note below).

```bash
cd infra

# Interactive (prompts for domain, DB name/user, Grafana, mail, backup, AWS, ACME, alertmanager):
./gen-env.sh .env

# Silent (all random, domain from $PANEL_DOMAIN or default panel.example.com):
PANEL_DOMAIN=panel.example.com ./gen-env.sh --silent .env
# or explicitly:
PANEL_DOMAIN=panel.example.com ./gen-env.sh .env

# Review and harden:
cat .env            # ensure PANEL_URL=https://panel.example.com
chmod 600 .env .metrics-token
ls -l secrets/      # postgres_password, forge_master_key, daemon_node_token, api_auth_secret, app_key
```

### Production (required — never deploy `compose.yml` alone on public host, `README.md:259-262`)

```bash
cd infra

# 1. Host directories (compose mounts these):
sudo install -d -o "$USER" -g "$USER" /srv/game-panel/servers /var/backups/gamepanel/postgres

# 2. Bootstrap control plane first (DB → API → Web) — loops back via SSH tunnel until TLS:
./bootstrap-control-plane.sh
# Internally: docker compose -f compose.yml -f compose.production.yml --env-file .env config --quiet
#             docker compose ... up -d --build postgres redis api web

# 3. Tunnel to complete setup (API/Web are loopback-only in production):
ssh -L 3000:127.0.0.1:3000 user@your-vps
# Open http://localhost:3000/setup → create first admin + first Beacon node
# Copy the issued DAEMON_NODE_ID and DAEMON_NODE_TOKEN into infra/.env, replacing the bootstrap values.

# 4. Start full production stack:
docker compose -f compose.yml -f compose.production.yml --env-file .env up -d --build
docker compose -f compose.yml -f compose.production.yml --env-file .env ps
docker compose -f compose.yml -f compose.production.yml --env-file .env logs --tail 200
```

## 8. Migrations

Migrations run **automatically on Forge API startup** — no manual step in the happy path.

- Entrypoint: `forge/api/cmd/api/main.go:189` calls `connected.RunMigrations(ctx, env("MIGRATIONS_DIR", "migrations"))` within a `10*time.Minute` startup context (`main.go:125`). Also `eventstore.Migrate` and `MigrateOperationalSecrets` (encryption rotation).
- Source: `forge/api/migrations/` (SQL files `001_init.sql` → `052_...` plus `BATCH2_MIGRATIONS_DIR=/batch2-migrations`), and `forge/api/cmd/api/river.go:runRiverMigrations` for the durable queue (`river_schema_migrations` table).
- Behavior: fresh DB → apply all; existing DB → apply delta only (idempotent, rerun-safe). Production guard (`scripts/cleanup/production-guard.sh`) validates the loaded `.env` before rollout.

Manual verification/re-run:

```bash
# Inside infra stack, check migration count (exposed via /api/v1/health/ready details.migrationCount):
curl -s http://127.0.0.1:8080/api/v1/health/ready | jq .details

# Or query postgres directly:
docker compose -f compose.yml -f compose.production.yml --env-file .env exec postgres \
  psql -U gamepanel -d gamepanel -c "SELECT version FROM river_schema_migrations ORDER BY version;"

# Fresh migration proof (CI pattern): start empty postgres + run api --healthcheck after deploy
```

If API fails to become healthy, inspect:

```bash
docker compose -f compose.yml -f compose.production.yml --env-file .env logs api postgres --tail 300
# Look for "RunMigrations" errors, missing DATABASE_URL, or FORGE_MASTER_KEY issues
```

## 9. Seed & First Access

**Seed is environment-gated (`forge/api/cmd/api/main.go:137-213`):**

| `APP_ENV` | `API_SEED_DEMO` | Behavior |
|---|---|---|
| `production` | `false` (default, enforced) | **No seed**. Must use `/setup` wizard. `API_SEED_DEMO=true` is rejected (`demoSeedEnabled` error). |
| `development` / `local` / `test` | `true` | `connected.Seed(ctx)` inserts demo admin/node/server `44444444-4444-4444-8444-444444444444`, then `clustermanager.ProvisionRecoveredServer` retries 15×2s to materialize the beacon workload. |
| any other | any | Seed disabled; error if `API_SEED_DEMO=true` outside allowed envs |

**First access (production):**

1. With the control plane bootstrapped (§7 step 2), open `https://panel.example.com/setup` (or via `ssh -L 3000:…` + `http://localhost:3000/setup` before TLS).
2. Create the first administrator — this endpoint is single-use; subsequent hits redirect to login.
3. Log in → **Admin → Nodes** → Create node → copy `DAEMON_NODE_ID` and `DAEMON_NODE_TOKEN` (`<id>.<secret>`) into `infra/.env`, restart daemon:

```bash
cd infra
# edit .env: DAEMON_NODE_ID=<uuid>  DAEMON_NODE_TOKEN=<id>.<secret>  PANEL_API_URL=https://panel.example.com/api/v1
docker compose -f compose.yml -f compose.production.yml --env-file .env up -d daemon
curl --fail http://127.0.0.1:9090/health   # beacon health (also via 127.0.0.1:9090/health from compose.yml:307)
curl --fail http://127.0.0.1:8080/api/v1/health/ready
```

**Development:**

```bash
npm run dev:start   # auto-creates DAEMON_NODE_TOKEN, seeds demo admin
# Then open:
open http://localhost:3000/setup   # first admin (if not seeded)
open http://localhost:3000         # dashboard
```
