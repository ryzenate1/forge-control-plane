# Subagent 01 — Backup Repository / Snapshot / Chunking / Deduplication Model — Kopia & Restic Comparison

**Dimension:** REPOSITORY / SNAPSHOT / CHUNKING / DEDUPLICATION MODEL  
**Cluster:** kopia (master), restic (master)  
**Forge scope:** `forge/api/internal/services/backup/*`, `forge/api/store/*` (`store_backups*.go`), `forge/api/migrations/*backup*`, `beacon/internal/backup/*`, `forge/web` backup pages

## 1. Reference Models (condensed)

### Kopia — content-addressed pack repository
- **Blob storage:** `repo/blob.Storage` interface (`PutBlob/GetBlob/DeleteBlob/ListBlobs` with offset/length, atomic `Put`, read-after-write) `reference/backup/kopia/repo/blob/storage.go:204-227`. Backends filesystem/s3/gcs/azure/b2/sftp all implement `Volume+Reader` contract.
- **Content manager:** `repo/content.WriteManager` (`reference/backup/kopia/repo/content/content_manager.go:70-124`) chunks arbitrary data into content IDs `ID = hash(compressed+encrypted payload)` via `WriteContent` (`content_manager.go:791-843`). Deduplicates by content-ID lookup (`getContentInfoReadLocked`) before enqueue; pending packs aggregate many contents into ~20 MB pack blobs (`pendingPackInfo` `content_manager.go:107-113`) with `p` / `q` prefixes (`PackBlobIDPrefixes` `content_manager.go:51-54`), protected by `pendingPacks map[blob.ID]*pendingPackInfo` + `packIndexBuilder index.Builder` (`content_manager.go:87-93`). Pack index shards are built (`BuildShards` `content_manager.go:459`) and committed as index blobs (`writeIndexBlobs` `content_manager.go:426-437`), flushed atomically with session marker (`flushPackIndexesLocked` `content_manager.go:448-501`). Encryption+compression per content (`maybeCompressAndEncryptDataForPacking` before lock).
- **Indexes:** `repo/content/index` + `indexblob` handle sharded, cacheable indexes. `committed_content_index*` (`repo/content/committed_content_index*.go`) is cached on disk/mem; recovery via `content_index_recovery.go`. Index version negotiated (`DefaultIndexVersion=2` `content_manager.go:43`).
- **Snapshots:** `snapshot.Manifest` (`reference/backup/kopia/snapshot/manifest.go:18-40`) stores `Source{host,user,path}`, `RootEntry *DirEntry` (`manifest.go:121-131`) with per-entry `ObjectID`, plus `DirManifest` sorted entries (`manifest.go:157-164`). Snapshot storage is merkled via `repo/object` IDs; `snapshot/snapshotfs` walks/reconstitutes trees with deduped file objects. Manifests themselves are content (`manifest.ContentPrefix="m"` `manifest/manifest_manager.go:36`) stored via `contentManager.WriteContent` (`manifest_manager.go:72-99`) with pendingEntries+Flush (`manifest_manager.go:214-224`) and compaction.
- **Maintenance/GC:** GC mark-sweep via `snapshot/snapshotgc` + `snapshot/snapshotmaintenance` + `repo/maintenance`. Unreferenced packs are deleted only after safe epoch (`epoch`-managed). Index compaction merges shards.

### Restic — pack + index + lock repository
- **Repository:** `internal/repository.Repository` (`reference/backup/restic/internal/repository/repository.go:32-57`) with `treePM` / `dataPM` packer managers (`repository.go:608-609`), target pack size 16 MiB (`DefaultPackSize` `repository.go:29`, `MinPackSize 4 MiB`, `MaxPackSize 128 MiB`). `saveBlob` (`repository.go:1017-1045`) deduplicates via `idx.AddPending` — `known = !AddPending(handle,size)` — no redundant `saveAndEncrypt`.
- **Chunking:** CDC via `restic/chunker` Rabin fingerprints (`chunker.Pol` `reference/backup/restic/internal/repository/chunker.go:21-27`, `Repository.ChunkerFactory` `chunker.go:45-47`). `chunker.MaxSize`/`MinSize` (512 KiB–8 MiB) drive content-defined boundaries. `cmd_backup.go` runs chunker loop: split → `Hash(buf)` (`repository.go:1024-1031`) → blob save. `zeroChunk` fast-path for sparse zeros (`repository.go:1348`, `1028`).
- **Indexes:** `internal/repository/index.MasterIndex` (`index/master_index.go`) aggregates many `index.Index` files loaded in parallel (`Repository.LoadIndex` `repository.go:712-755`, `createIndexFromPacks` `repository.go:760-825`). Pack header `pack.List` (`repository.go:969-984`) maps `<packID → blobs>`. Indexes are rewritten on prune via `rewriteIndexFiles` after filtering `ignorePacks`.
- **Snapshots/Trees:** `internal/restic` snapshot JSON references tree blobs; trees themselves are blobs. Blob types `DataBlob/TreeBlob` (`reference/backup/restic/internal/restic/blob.go:38-43`) determine pack placement and `IsMetadata`.
- **GC/Prune:** `repository/prune.go:106-176 PlanPrune` — duplicate detection (`packInfoFromIndex` `prune.go:178-347`) with overflow-saturated counts, followed by `decidePackAction` (`prune.go:386-582`) applying percentile target pack size (`calculateTargetPacksize` `prune.go:351-384` → `0.8 * max(4 MiB, p3)`). Keeps packs with `exclusive lock` required. Execute: repack blobs via `CopyBlobs`, rebuild index, delete packs (`prune.go:594-690`).
- **Locking:** File locks in backend (`internal/repository/lock.go:47-110 LockRepo`) with `exclusive` flag, 5 min refresh ticker (`refreshLocks` `lock.go:124-186`), stale detection (`monitorLockRefresh` `lock.go:188-248`), `RemoveStaleLocks`/`RemoveAllLocks` (`lock.go:270-303`). `check --read-data`, `prune` require exclusive; backup needs non-exclusive.

## 3. Logic Findings (3 high-impact, file:line anchored)

### LF-01 — Whole-archive buffering on encrypted upload creates OOM & stalls (service staging lifecycle)

**Root cause.** `forge/api/internal/services/backup/service.go:271-351` `UploadBackupWithOptions` treats the post-compress/post-encrypt pipeline as `io.Reader`s (`CompressReader` → `EncryptReader` each returning `io.Pipe` at `compression.go:63-97` / `encryption.go:150-162`), then immediately `io.ReadAll(data)` (`service.go:303-304`) into `dataBytes []byte`. For a 40 GiB world, the API pod holds 40 GiB + zstd overhead + hex nonce copy in heap before single `adapter.Upload(ctx, backupPath, dataBytes)` (`service.go:316`). `DownloadBackupWithOptions` (`service.go:357-395`) similarly `adapter.Download` into `data []byte` (`368-372`) then decrypt/decompress in-place — doubling heap. The streaming adapters (`StorageAdapter.UploadStream`/`DownloadStream` at `storage.go:35,38`) are bypassed on the encrypted path.

That negates `LocalBackup.Create`'s own streaming design (`local.go:298-328` `zip.NewWriter(zipTarget)` with optional `rateLimitedWriter` at `local.go:292-295` which correctly streams to temp file). The beacon `S3Backup.uploadToS3` (`s3.go:272-286` `os.Open(localPath)` → `manager.Uploader.Upload`) streams from file and does not OOM, but the hot scheduling path (`worker.go:222-273 executeServerBackup`) calls daemon `CreateBackup` which goes through beacon local → S3 streaming, so the OOM only hits the direct `UploadBackup*` API used by manual uploads and DB-volume backups via service layer. `beacon/internal/backup/scheduler.go:60-66` backup callback also streams.

**Impact.** API pod with default 512 MiB limit crashes on any backup > ~300 MiB encrypted; no `maxS3DownloadBytes` analog (`beacon/internal/backup/s3.go:28` caps at 50 GiB) on upload.

**Fix.** Rewire `UploadBackupWithOptions` to `UploadStream` pipeline: `r → CompressReader → EncryptReader → pipe → adapter.UploadStream` with fixed chunk framing (or multipart upload). Same for download.

### LF-02 — GC has no reachability index; retention deletes storage-orphaning rows and misses orphaned objects

**Root cause.** Forge GC is count/age filter over the `backups` row, not mark-sweep over content-graph.

- **Row-only delete path:** `forge/api/internal/store/store_backups.go:242-259` `CleanupOldBackups` executes `DELETE FROM backups WHERE is_locked=FALSE AND created_at < now()-interval '1 day'*$1 AND status='completed'` (`store_backups.go:248-253`) — single SQL `DELETE`, never touches object storage. The sibling `CleanupOldBackupsForServer` (`store_backups.go:263-301`) combines age `OR` subselect `IN (SELECT uuid ... LIMIT GREATEST(0,COUNT-status_completed - $3))` (`store_backups.go:287-294`) — also DB-only. If any caller invokes these (crons, `seeder` retention 30 days `migrations/019`+`seeder` init), the S3/GCS/Azure blob remains forever (orphan). The correct path is `service.go:689-741 CleanupExpiredBackups` and `service.go:743-784 EnforceRetentionPolicy` which call `DeleteBackupFromStorage` then `DeleteBackup` per row, but they are not the sole callers.

- **Orphan in opposite direction:** Beacon `S3Backup.List` (`s3.go:163-207`) lists via `ListObjectsV2` + per-object `HeadObject` to read checksum metadata (`s3.go:187-203`). If the `backups` row was deleted via the SQL path, the object still appears in that listing but `store.ListBackups` (Forge panel) no longer shows it — UI (`backups-view.tsx:69` `list = backups.data?.data`) and beacon disagree.

- **No size validation before delete:** Restic's `decidePackAction` aborts if `calculated size != real size` (`prune.go:411-415` → `ErrSizeNotMatching`); Forge `store_backups.go:281` `DELETE ... IN (SELECT uuid ... ORDER BY created_at ASC LIMIT ...)` is not deterministic under concurrent inserts and can delete the just-completed newest backup before `FailStaleBackups` finalizes it.

- **Idempotency without lock:** `worker.go:401-448 enforceRetentionBeforeBackup` counts completed unlocked (`414-418`), computes `overLimit = count - maxBackups +1` (`422-423`), then iterates oldest-first `toDelete` and calls `DeleteBackupFromStorage`/`DeleteBackup` without `FOR UPDATE SKIP LOCKED` or transactional `DELETE RETURNING`. Two API replicas each compute same `overLimit` and race to delete same rows — second `DeleteBackup` returns `backup not found` swallowed (`436-442` `continue`), but `DeleteBackupFromStorage` already re-deleted the same S3 key (idempotent) while metrics double-count.

**Impact.** Long-run storage bill grows with orphans; worst case retention deletes the most recent live backup needed for restore.

**Fix.** Remove the DB-only `CleanupOldBackups*` callers or make them invoke storage deletion in a transaction; adopt `DELETE ... RETURNING` + storage delete; schedule a nightly `ListObjectsV2` vs `SELECT uuid` reconciliation (analogous to Restic `check --read-data` / Kopia `content verify`).

### LF-03 — No cross-host distributed lock; in-memory namespace mutex cannot prevent split-brain double-create and torn restore

**Root cause.** Beacon protects `Create`/`Restore` with an in-process map mutex `LocalBackup.namespaceOps` (`local.go:49-50` `namespaceOps map[string]*namespaceOperation{mu,refs}`, `lockNamespace` `local.go:90-109` ref-counted `operation.mu Lock` + defer `refs--`). This serializes two concurrent `Create` calls targeting the same `namespace` on the same daemon process (`local.go:239-240` first line of `Create`). It does **not** serialize across two daemon replicas serving the same server (scaled beacon deployment or host failover), nor across API replicas that each dispatch `Worker.executePolicy` (`worker.go:125-141` loop over `ListAllEnabledPolicies` every minute) without advisory lock.

Evidence of split-brain:
- `worker.go:201-220 executePolicy` looks up `ServerControlTarget` then branches `executeServerBackup/Database/Volume`. The DB pending row uses `UpsertBackup` with `ON CONFLICT(server_id,name) DO UPDATE` (`store_backups.go:64-98` `ON CONFLICT(server_id,name)`). Two workers that happened to generate same `name = fmt.Sprintf("backup-%s", now.UTC().Format("20060102T150405Z"))` (`worker.go:211`) with same second truncate produce same `(server_id,name)` and the second overwrites the first's pending row, losing its UUID.
- The daemon side second `Create` then attempts `OpenFile(backupPath+".partial", O_CREATE|O_EXCL,0600)` (`local.go:275`) which fails `exists` for the local path if both went to same daemon, but if they landed on different daemons each has isolated `backupRoot`/`s3 prefix` and both succeed — two S3 objects with same logical name but different `checksum`/`size` race to `UpsertBackup` (`worker.go:256-268` second `Upsert` with `entry.UUID/entry.Name/entry.Checksum`).

Restore has stronger local protection via 3-phase journal (`local.go:572-623` `restoreJournal{Staging,Rollback,Phase}` + `writeRestoreJournal` `899-929` + `recoverInterruptedRestore` `931-999` + `RecoverRestoreJournals` `867-893`), butjournal path is `filepath.Dir(serverRoot)/"."+basename+".restore-journal.json"` (`local.go:895-897`) — local FS only. Two daemons restoring same S3 object to shared `serverRoot` (NFS/Gluster) would each create their own journal in its own `parent` directory and not see the other's `live-moved`.

Contrast: Restic `lock.go:47-111 LockRepo(exclusive, retryLock, printRetry)` writes a lock file in the **backend** and refreshes it (`refreshLocks` `lock.go:124-186`) with stale detection (`monitorLockRefresh` `lock.go:188-248`); `prune` demands exclusive and fails if any non-exclusive lock exists. Kopia uses storage-level session markers plus `blob.Storage` atomicity.

**Impact.** Duplicate backups waste storage and create ambiguous "latest" (UI shows `ORDER BY created_at DESC` `store_backups.go:18-19` but two rows with same `name` collide). Torn restore can interleave journal phases and leave `parent/.rollback-*` dirs orphaned.

**Fix.** Add backend-anchored lock: either `pg_advisory_xact_lock(hashtext(server_id))` around `executePolicy` transaction, or S3 lock file `locks/backup-<serverID>.json` with TTL+refresh (mirror Restic). Gate `Worker.tick` with single-leader election (existing `queue/leader.go`).
