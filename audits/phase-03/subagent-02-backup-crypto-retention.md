# Subagent 02 — Backup Crypto / Retention / Verification / Storage — Kopia & Restic Comparison

**Dimension:** ENCRYPTION / KEY MANAGEMENT / INTEGRITY / VERIFICATION / RETENTION / PRUNING  
**Cluster:** kopia, restic  
**Forge scope:** `forge/api/internal/services/backup/*`, `beacon/internal/backup/*`, `forge/api/internal/secrets/keyring.go`, `forge/api/internal/store/store_backup*.go`, `forge/api/internal/store/store_backups.go`

---

## 1. Reference Models

### Kopia
- **Encryption:** AES-256-GCM authenticated encryption per content blob; key hierarchy via HKDF-SHA256 derived per-purpose keys from master key; per-blob random nonce; chunk storage is content-addressed and always encrypted. `repository` package enforces encryption before any blob touches storage. KMS integration supports key rotation via key versions.
- **Integrity:** Content hash (BLAKE2/SHA256) stored in index; Merkle-like manifest integrity; `snapshot verify` / `repository validate` re-hashes on download.
- **Retention/Pruning:** Snapshot retention policy (keepLatest, keepDaily, keepWeekly, etc.) expressed as *union* (OR) — a snapshot is kept if it matches *any* rule. Maintenance compacts indexes and deletes unreferenced blobs; epoch manager coordinates concurrency via distributed locks.
- **Locking:** Repository locking via `index` + `epoch` + blob storage atomics; server mode coordinates writers.

### Restic
- **Encryption:** `internal/crypto` uses **AES-256-CTR + Poly1305-AES** (AEAD) — 32-byte key split into 16-byte AES key + 16-byte Poly1305 key, per-blob random nonce (16 bytes), no nonce reuse. All repository data (blobs, trees, snapshots) is encrypted; keys derived via `scrypt` from user password stored in `Key` file. AEAD provides integrity.
- **Verification:** `cmd_check.go` checks repository structure, pack integrity, index vs data, snapshot tree traversals; `--read-data` re-reads pack payloads and verifies MAC.
- **Retention:** `cmd_forget.go` / `cmd_prune.go` — `ForgetPolicy` (KeepLast, KeepHourly, KeepDaily, KeepWeekly, KeepMonthly, KeepYearly, KeepTag) with `keep*` semantics as union: snapshots surviving any rule are retained; locked snapshots are always retained. `prune` rebuilds index, removes unreferenced packs; requires exclusive lock. Lock files prevent concurrent prune vs backup.
- **Storage backends:** Abstraction in `internal/backend` with local, S3, GCS, Azure, SFTP, etc.; retries, `List` semantics, locking via lock files in backend.

## 3. Logic Findings (4 high-impact)

### L1 — Unauthenticated Checksum Sidecar + Null-AAD GCM enables transplant/forgery
**Severity:** High — integrity failure.

- `beacon/internal/backup/local.go:787-817` `writeMetadata` writes `localMetadata{Checksum: sha256, Size, Created}` as plain JSON adjacent to `.zip` (`os.CreateTemp`+`Rename`). `beacon/internal/backup/verification.go:64` verifies by comparing recomputed SHA-256 to `info.Checksum` fetched from sidecar/S3 metadata. The sidecar is unkeyed; an attacker with access to backup storage (shared S3 bucket, local FS traversal) can overwrite both the archive and the sidecar consistently, or modify checksum to match tampered archive. Similarly, `service.go:513-545` `VerifyStorageReceipt` re-downloads and SHA-256 checks, not AEAD MAC.
- Forge encryption at `encryption.go:119` uses `gcm.Seal(nil, nonce, data, nil)` — empty AAD. Combined with unauthenticated checksum, ciphertext malleability is limited by GCM MAC but AAD=null means a backup ciphertext for `server-A/backup-20260101T000000Z.zip` validates identically when restored under `server-B` if filename is spoofed, because `BackupInterface` trusts `namespace`/`name` supplied by caller (`backup.go:59-69` `BackupInterface` comment notes namespace is caller-validated but `validNamespace`/`validBackupName` only check charset/length). Restic avoids this by encrypting snapshot JSON that includes hostname and by content-addressed IDs; Kopia binds content IDs.
- **Impact:** Silent restore of wrong-server data (cross-tenant if prefix misconfigured), or acceptance of tampered backups where checksum sidecar was also updated.

### L2 — Streaming bypass (O O M) — `EncryptReader`/`DecryptReader` buffer entire backup in heap
**Severity:** High — availability / DoS.

- `forge/api/internal/services/backup/encryption.go:150-175` / `178-204`: both `io.ReadAll(r)` entire input before `encryptWithKey`/`decryptWithKey`, then construct `io.Pipe` that immediately writes buffered `encrypted` and closes. The returned `io.Reader` merely replays the in-memory buffer — not streaming. `service.go:303` `dataBytes, err := io.ReadAll(data)` then `adapter.Upload(ctx, backupPath, dataBytes)` similarly loads whole post-compress/post-encrypt backup into heap and then copies into storage adapter which may copy again.
- For a 20 GiB game world (Forge advertises "world growth"), API RAM spikes by ≥20 GiB plus S3 SDK buffering, OOM-killing the `api` pods (all services share 1 GiB limit in `infra/compose.yml` baseline). The beacon S3 stager (`beacon/internal/backup/s3.go:126-136` `s.local.Create` → `s.local.archivePath` then `uploadToS3` via `s.uploader.Upload` streaming from `os.Open(localPath)`) does stream, but service path clobbers it by loading first.
- Beacon `LocalBackup.Create` streams ZIP creation via `zip.NewWriter(zipTarget)` but `zipTarget` wraps `rateLimitedWriter` correctly — local-only path is OK. Encryption/compression test `encryption_test.go:179-203` `TestEncryptLargeData` uses 100 KiB fixture — too small to catch.
- **Fix:** Implement chunked GCM-SIV streaming (e.g., `cipher.StreamWriter`) or per-chunk encryption with 64-KiB frames and length-prefix, as Kopia (`content-manager` chunked) and Restic (`pack` 16-MiB) do. At minimum, wire `UploadStream`/`DownloadStream` through `io.Pipe` without intermediate `ReadAll`.

### L3 — Retention semantic inversion causes silent data loss or retention bypass
**Severity:** High — correctness / data loss.

- Three implementations enforce different logics:
  1. `beacon/internal/backup/retention.go:35-123` comment explicitly says "Intersection: a backup must satisfy ALL active rules to be kept" — AND semantics.
  2. `forge/api/internal/services/backup/service.go:743-784` `EnforceRetentionPolicy` computes `keep = isLocked || (withinCount && withinAge)` — AND.
  3. `beacon/internal/backup/retention.go:79-102` `KeepDaily/KeepWeekly/KeepMonthly` loops set `keep=true` for period buckets *outside* of `MaxAge` filter, then `MaxBackups` intersects — a backup rejected by `MaxAge` can be re-added by `KeepDaily` rule, contradicting AND comment.
- Restic and Kopia retention are **union (OR)**: a snapshot is retained if it matches *any* retention bucket (KeepDaily *or* KeepWeekly *or* MaxBackups). AND semantics delete strictly more. Example: policy `MaxBackups=10, RetentionDays=7, KeepDaily=1, KeepWeekly=1` with 20 backups aged 10 days. Restic would keep ≈10 (last 10 or one per bucket); Forge AND (`withinCount && withinAge`) keeps 0 unlocked because `withinAge=false` for old, so intersection empties. Safety rail `retention.go:122` `keep[backups[0].ID]=true` only saves the single most recent, discarding 9 more days of history unexpectedly.
- Conversely, beacon `KeepDaily` re-addition can retain backups *older* than `MaxAge`, bypassing age limit entirely — so depending on which implementation is active, the same policy either over-deletes or under-deletes.
- `store/store_backups.go:240-259` `CleanupOldBackups` uses `DELETE ... WHERE created_at < now() - interval '1 day' * $1 AND status='completed'` — ignores `is_locked`? No, includes check? Actually query at `250-251` `WHERE is_locked=FALSE AND ...` — correct. But `store/store_admin_backups.go:218` listing filter excludes `status='deleted'` but not `status='failed'` — retention policy `ArtifactService.ApplyRetentionPolicy:730-744` iterates `index >= MaxBackups` without filtering `status` → prunes `failed` artifacts spuriously and skips pagination (only `Page:1,PerPage:200` then slice `filter:735`).
- **Impact:** Operator observes unpredictable expiry; compliance retention violated.

### L4 — Orphan leaks from SQL-only prunes + double-delete race
**Severity:** High — storage cost & integrity.

- `store/store_backups.go:242-259` `CleanupOldBackups` and `277-301` `CleanupOldBackupsForServer` delete DB rows via single `DELETE FROM backups WHERE ...` without calling `DeleteBackupFromStorage`. The parallel correct path `service.go:689-741` `CleanupExpiredBackups` and `743-784` `EnforceRetentionPolicy` do call `DeleteBackupFromStorage` before `DeleteBackup`. Two maintenance callers exist: `queue/periodic.go` for `backup.retention` hourly and `worker.go:401-446` `enforceRetentionBeforeBackup`. If `CleanupOldBackups` is still invoked from handler/cron, storage orphans accumulate; S3 `List` before billing will show diverging counts.
- `beacon/internal/backup/s3.go:163-207` `List` re-derives `BackupInfo` by `HeadObject` per key (`187-190`); orphan files with no DB row appear in beacon list but not in panel `ListBackups` (DB-driven) — user sees different counts on beacon vs panel.
- Race: `worker.go:406-444` `enforceRetentionBeforeBackup` does `store.ListBackups(cleanupCtx, serverID, 1,1000)` then builds `toDelete` slice and calls `s.DeleteBackupFromStorage` then `s.store.DeleteBackup` without transaction; concurrent workers (two API replicas) each list same set, both attempt to delete same object — second `DeleteBackup` returns `RowsAffected()==0` → `ErrNoRows` silently swallowed at `413-444` `continue`. S3 `DeleteObject` is idempotent, so no error, but metric `cleaned++` in `service.go` increments per attempted delete, overstating. No `FOR UPDATE SKIP LOCKED` selection, so thundering herd on `ListRetryableBackupJobs` as well (`store_backup_jobs.go:199-232`).
- **Fix:** Single ownership: always delete storage first, then DB in `DELETE ... RETURNING` transaction; or adopt Restic-style mark-sweep with exclusive prune lock.

## 7. Recommendations

1. **Unify crypto under keyring** — Add `backup-encryption` purpose to `secrets.Keyring` with per-backup subkey `HKDF(activeKey, serverID+backupUUID)` and envelope header `forge:v1:<keyID>:<nonce||seal>`. Store `Nonce` no longer as separate DB column. Support re-encryption on key rotation.
2. **Stream encryption** — Implement `EncryptedWriter`/`EncryptedReader` chunked framing (e.g., 64 KiB plaintext → `nonce(4-byte seq)+GCM`) and wire `UploadStream`/`DownloadStream` end-to-end; remove all `io.ReadAll` on encrypted path. Match Kopia's `encrypted_storage` wrapper.
3. **Retention consolidation** — Extract single `RetentionEngine` library used by beacon and service; property-test against Restic `Forget` vectors (union, locked-exempt). Remove `store_cleanup*` SQL-only path; route through engine that deletes objects then rows atomically and accounts `backup_storage_receipts`.
4. **Scheduled verification** — Add `BackupVerifyScheduler` analogous to Kopia maintenance / Restic `check --read-data --with-cache`, persisting `LastVerifiedAt` and forcing full re-hash at least weekly for locked/sensitive backups, not skipping `IsVerified`.
5. **Distributed lock for prune** — Introduce repository lock file (e.g., `locks/backup-*.json` in S3) or DB advisory lock around `EnforceRetentionPolicy`/`CleanupExpiredBackups`; require exclusive lock for `prune` equivalent, as Restic does.
6. **Fix pre-restore snapshot** — Actually snapshot current server files to a temporary backup file (reuse `LocalBackup.Create`) before destructive truncate restore, persist receipt, and delete on success — not just a DB record.
