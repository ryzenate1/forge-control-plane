# Phase 5 — Subagent 3: Runtime / System Containers / VMs / Clustering (Incus + NetBird vs Forge)

Cluster: `incus` (reference/orchestration/incus), `netbird` (reference/orchestration/netbird)
Dimension: Incus (containers+VMs, images, storage pools, networks, profiles, projects, clustering, migration/live-migration, snapshots) and NetBird (WireGuard overlay, identity, peers/groups, access policies, routing, DNS, management plane) vs Forge's runtime adapters and networking abstractions.

**Verdict up front:** Forge's runtime story is a façade over Docker. The control plane registers **seven** provider names (`docker containerd podman firecracker kubernetes lxc kvm`), but the node agent only implements five, its factory has no `lxc`/`kvm` branch at all, and the beacon's create handler silently discards the `provider` field and always answers `"mode": "docker"`. LXC and KVM are labels that degrade to a Docker container on the far side of the wire. The Firecracker runtime that does exist boots every microVM from the *same* rootfs image mounted read-write, configures *no* network interface, and hardcodes install exit code 0. Migration exists only as stop-archive-copy-restore (cold); the capability system (`snapshots`, `live_migration`, …) that would advertise the difference is dead code — nothing calls `CheckCapability`. On the networking side, Forge has **no overlay option whatsoever**: the Node schema has no private/tunnel address, the gateway resolves targets to public hostnames, service discovery is an admin-only manual registry whose reaper marks everything unhealthy 3 minutes after registration, and the only occurrence of "WireGuard" in product code is a test assertion string. Incus solves each of these (profile composition, storage drivers, CRIU/QEMU live migration, dqlite membership, evacuation) and NetBird solves the mesh (self-registering peers, group policies, routed prefixes, DNS distribution) with far less surface than Forge's partials. Recommendations: either delete the phantom providers or implement them behind an honest capability report; adopt NetBird-style self-registration for servicediscovery before trusting any of it.

## 0. Wiring reality check (what is actually live)

**Control plane (`forge/api`):**
- Provider enum has 7 values: `forge/api/internal/runtime/runtime.go:9-16`.
- Adapters registered in `forge/api/cmd/api/main.go:389-399` — including `NewLXCAdapter` (:398) and `NewKVMAdapter` (:399).
- A second, older runtime abstraction coexists: `forge/api/internal/services/runtime/runtime.go:8-14` (`RuntimeDocker|RuntimeBeacon|RuntimeCustom`) — three overlapping registries total.
- Servicediscovery is wired (`main.go:987-990`) but its only writer is an admin HTTP route: `forge/api/internal/http/handlers_servicediscovery.go:55-70` (`requireRole("admin")`). No beacon ever registers an endpoint (zero references to servicediscovery/discovery under `beacon/internal/`).

**Node agent (`beacon`):**
- Factory supports exactly docker/podman/kubernetes/containerd/firecracker — `beacon/internal/runtime/factory.go:19-31`; `AvailableProviders()` lists 5 (:45-53). There is **no** `lxc.go` or `kvm.go` under `beacon/internal/runtime/`.
- Firecracker is compile-gated: `beacon/internal/runtime/firecracker.go:1-2` (`//go:build firecracker`); without the tag you get an error stub `provider_firecracker_disabled.go:7-9`.
- The HTTP create handler ignores the provider entirely — body struct has no `Provider` field (`beacon/internal/server/server.go:740-772`), dispatches to the single configured `s.runtime` (:829) and replies `"mode": "docker"` unconditionally (:841).

So when Forge's `LXCAdapter` sends `Provider: "lxc"` (`daemon/client.go:418` json `provider,omitempty`; set at `lxc.go:39`), beacon drops it on the floor. That chain is LF-1 below.

## 2. Logic findings

### LF-1 — LXC/KVM are phantom providers: the whole chain drops the label
Evidence chain: control-plane adapter sets `Provider: LXCProvider` into the daemon request (`lxc.go:39`, `daemon/client.go:418`) → beacon's create handler struct has **no** `Provider` field so the JSON key is discarded during decode (`beacon/internal/server/server.go:740-772`) → request executes against whatever single runtime the beacon booted with (`factory.go:19-31`; default docker) → response is hardcoded `"mode": "docker"` (`server.go:841`). Meanwhile `LXCAdapter.Capabilities()` returns the empty struct and `SupportsMigration()=false` (`lxc.go:19-21`), so even the adapter admits it has no LXC traits. Consequence: a user selecting "LXC" or "KVM" gets a Docker container, and because beacon's capability report leaves `RuntimeProvider` empty (`capabilities.go:95-108,170`), the panel can never detect it. This is worse than a stub — it's a silent lie across a trust boundary.

### LF-2 — The Firecracker runtime is unsafe-by-construction
- **Shared writable rootfs:** every VM uses `config.RootfsImage` directly as its RW root drive — `firecracker.go:262-269` (and again :436-443). Two concurrent instances boot the same ext4 file read-write → corruption. `Create()` merely registers an in-memory struct; it never clones a per-VM disk (:171-195).
- **No networking:** the runtime never issues a PUT to `/network-interfaces`; `Ports`/`NetworkName` from `CreateRequest` are ignored entirely (absent from `configureMicroVM` :249-293). Every microVM is born offline.
- **Install always "succeeds":** `InstallResult{ExitCode: 0}` is hardcoded regardless of guest behavior (:494); MMDS is used as a fake channel for a `script` + `mounts` payload (:456-464) that no guest agent consumes, and FC MMDS doesn't mount anything.
- **Fabricated stats:** `Stats` decodes `{"memory_usage_mb","cpu_usage_percent"}` out of `/metrics` (:712-723) — fields Firecracker never emits (its metrics are nested latency counters), so usage silently reads 0.
- Build-tag gate means most deployments get the error stub anyway (`provider_firecracker_disabled.go:7-9`) — which is the honest part of this file.

### LF-3 — The capability system is dead code that overstates reality
`Registry.CheckCapability` (`registry.go:98-110`) and `Capabilities.Supports` have **zero callers** outside their own definitions/tests; capability checks only feed metrics counters and registration events (:44-54). At the same time the presets assert unimplemented powers: `FirecrackerCapabilities(){Snapshots:true}` (`capabilities.go:118-125`) though no snapshot operation exists in any runtime interface (`beacon/internal/runtime/runtime.go:144-163`); `KubernetesCapabilities(){Migration:true}` (:127-135) though `SupportsMigration()` is false for every adapter including kubernetes (`kubernetesadapter.go:25-27`); KVM/LXC return empty caps (`kvm.go:19`, `lxc.go:19`) yet are registered next to presets that claim real ones (`main.go:395-399`). Compare Incus, where migration eligibility is computed per instance from actual state (`CanLiveMigrate` — `driver_lxc.go:9626`). Either wire placement/scheduling gates to `CheckCapability` or delete the struct.

### LF-4 — No overlay option for cross-node private traffic
The Node record carries only public coordinates (`store.go:132-191`); the traffic manager resolves routing rules to `node.PublicHostname || node.FQDN` (`trafficmanager/service.go:665-671`), so all inter-node service paths traverse public DNS/TLS. The one place an overlay was imagined is a test asserting a hardcoded `TargetHost: "10.210.1.5"` with the message *"expected remote WireGuard IP"* (`crossnode_test.go:843-857`) — there is no implementation behind the string anywhere in the repo. Reachability verification compounds this: `VerifyCrossNode(sourceNodeID, targetNodeID, …)` dials from the control plane, not from the source node (`reachability.go:58-79`), so even the diagnostic data about private links cannot exist. NetBird demonstrates the missing piece end-to-end: signed peer enrollment (`SyncPeer` w/ `WireGuardPubKey` — `account.go:1935`), NetworkMap fan-out (`account.go:457`), NAT-traversal fallback via relay over WS/QUIC (`relay/server/server.go:63-89`), and client-side route application (`routemanager/manager.go:115`). For a multi-node game-hosting panel (east-west DB replication, private admin SSH, tenant-isolated voice servers), Forge needs *an* answer here — embedding netbird, headscale-style coordination, or at minimum a tunnel-IP column + policy model.

### LF-5 — Fencing fires on recovery and fences nothing physical
`fencing.Service.Handle` reacts to `EventNodeRecovered` (`fencing.go:20-27` — published by `heartbeatmonitor/service.go:340`), i.e., fencing runs when a node *comes back*, bumping `Generation++` and stamping a fixed 24h lease on all its servers (:29-49). There is no revocation of network access, no workload relocation, no interaction with beacons. Contrast: Incus marks members offline after `offlineThreshold` (`heartbeat.go:113`, `db/node.go:89-96`) and drives rebalance/evacuation; NetBird policy removal cuts a peer's mesh access immediately via the next NetworkMap (`account.go:457`). Forge's mechanism protects only against stale-control-plane writes during a partition; calling it "fencing" oversells it, and triggering on recovery means the actual failure window is unfenced.

### LF-6 — servicediscovery is a write-only registry with guaranteed-unhealthy output
Endpoints enter the registry exclusively through an admin-only POST (`handlers_servicediscovery.go:55-70`); beacons/workloads never self-register (no reference anywhere under `beacon/internal/`). `LastHeartbeat` is stamped once at registration (`registry.go:91`) and no code path refreshes it — `UpdateEndpointStatus` writes only `Status`/`UpdatedAt` (:216-241). The reaper therefore transitions every endpoint to `unhealthy` once `heartbeatTTL=3m` elapses (`stale_reaper.go:26-27,104-117`), regardless of actual health. The NetBird contrast is structural: peers continuously re-sync and the server buffers/pushes updates to affected peers (`account.go:1741`), keeping state live without operator toil.

### LF-7 (minor) — Three overlapping runtime abstractions invite drift
`beacon/internal/runtime` (node-side, 5 providers), `forge/api/internal/runtime` (control-plane adapter interface w/ 7 names), and `forge/api/internal/services/runtime` (`docker|beacon|custom`, `services/runtime/runtime.go:8-14`) define three incompatible "Runtime" concepts with different method sets. `clustermanager` builds requests carrying `RuntimeType: target.RuntimeProvider` (`clustermanager/service.go:671-678`) while `CreateServerRequest.RuntimeType` (`runtime.go:66`) is consumed by nobody. Consolidate before implementing any new provider.

## 3. Does Forge need an overlay mesh? Profile stacking vs eggs?

**Overlay:** Yes, if multi-node is more than marketing. Today every cross-node promise leaks public exposure: gateway targets resolve to public hostnames (#10), migrations push archives node→node using public `NodeURL`s with short-lived bearer credentials (`migration/service.go:450-467`), and admin SFTP/console ride the same surface. A NetBird-style mesh (even just between beacons) would give: private east-west transport, instant cryptographic revocation on fence (#9), and truthful per-peer reachability (#13). Minimum-viable version: add `TunnelIP`/`MeshPubKey` to the Node schema, distribute via the existing heartbeat, and prefer it in `resolveTargetHost`.

**Profile stacking:** Forge should steal Incus's model, not Incus's syntax. Eggs-as-singletons force every combination (minecraft + gpu + backup-agent + region-limits) to be a new egg or a forked JSON blob; `ConfigFrom` gives one level of inheritance (`store_nests.go:50`). Incus's ordered-list merge with deterministic precedence and local override (`db/cluster/profiles.go:126-164`) plus existence/duplicate validation (`instance_utils.go:803-826`) is ~40 lines of Go and maps cleanly onto Forge's existing egg config JSON: `profiles: ["base-game", "gpu", "eu-only"]` with last-wins merge at provisioning time. Devices (ports, mounts, networks) belong in the same composition layer — today they exist only as flat request fields (`runtime.go:39-82`).

## 4. Priorities

1. **P0 — Stop lying about providers:** remove lxc/kvm from the registry until a beacon implements them, or make beacon reject unknown `provider` values instead of dropping them (LF-1, #16).
2. **P0 — Fix or quarantine Firecracker:** per-VM rootfs clone, network-interface setup, honest exit codes/stats (LF-2). Until then keep the build-tag stub as the only path.
3. **P1 — Mesh decision:** adopt/integrate an overlay (NetBird-compatible or simpler) and add tunnel addressing to Node + traffic manager (LF-4).
4. **P1 — Make servicediscovery self-registering:** beacon heartbeats should carry endpoint liveness (fixes LF-6 and makes the reaper meaningful); move reachability probing to beacons.
5. **P2 — Profile composition over eggs** (§3) and retire the third runtime abstraction (LF-7).
6. **P2 — Wire or delete the capability system** (LF-3): scheduler/placement should consult `CheckCapability` before assigning workloads to nodes.
