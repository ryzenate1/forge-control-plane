**Scope:** `reference/app-platforms/1panel/agent/app/api/v2/{container,image,image_repo,docker,cronjob,snapshot,monitor,firewall,ssh,fail2ban,host,file,ftp,process}.go` + `agent/app/model/*` vs `beacon/internal/server/{handlers_host,handlers_firewall,container_admin,hostfiles,sysinfo_linux}` + `beacon/internal/metrics` + `beacon/internal/activity` + `forge/api/internal/http/{handlers_host,handlers_files,handlers_firewall,handlers_cronjob,handlers_allocations}` + `forge/api/internal/services/{cronjob,heartbeatmonitor,observability,backup}` + `forge/web/app/admin/{host,firewall,cron-jobs,files,docker,monitoring}` + migrations.

**Date:** 2026-08-23

## 1. Executive Summary

1Panel is a **single-host control panel** with fully local infra primitives: Docker daemon config (`daemon.json`), firewall (ufw/firewalld + iptables chains), SSH/fail2ban/FTP, multi-host SSH inventory, snapshot-as-system-restore, and deep file manager (1.4k-line `file.go`). Forge is a **fleet orchestrator**: Beacon agents per node expose system telemetry and Docker via an admin-scoped Docker API, while Forge API acts as a **proxy/routing layer** (`handlers_host.go`, `handlers_firewall.go`, `handlers_files.go`) to the selected node. Monitoring is split: Beacon `metrics`/`sysinfo_linux` for OS probes + Prometheus histogram `handlers_metrics.go`, and Forge `observability/metrics_collector.go` + `heartbeatmonitor` for node health. Forge has **no parity** for SSH daemon management, fail2ban, FTP, daemon.json tuning, or system-wide snapshots; its backup system is instead **workload-scoped** (server/database/volume adapters with S3). The largest parity gaps cluster in firewall strictness, cronjob dispatch topology, file allowlisting, and monitoring synthetic-data fallback.

## 3. Deep Dive — Representative File:Line Walkthroughs

### Docker / Container delta
- 1Panel compose lifecycle fully present (`container.go:263`–`352` search/test/create/operate compose, `:882` `LoadComposeEnv`) — Forge has **no compose orchestration** (containers are Wings-managed servers, not user composes; `handlers_allocations.go:9` only allocates ports).
- Forge container exec is allowlisted (`container_admin.go:832` `allowedCommands` map — `ls/pwd/ps/top/df/free/uname/...` only, `:844` checks `command != path.Base(command)`), blocking shell metacharacter abuse. 1Panel has no comparable exec allowlist in `container.go`; exec is unrestricted (inside `containerService.ContainerExec` via service layer).
- 1Panel `ContainerListStats` (`container.go:418`) aggregates stats across all containers; Forge `handleContainerStats` (`container_admin.go:995`) returns `ContainerStatsOneShot` for a single container.

### Firewall audit & persistence
- Forge persists to `firewall.json` (`handlers_firewall.go:259` `persistLocked`: `MkdirAll 0700`, `MarshalIndent`, `CreateTemp`+`Chmod 0600`+`Write`+`Sync`+`Rename`+`syncDirectory`) — durable against crashes. 1Panel firewall persistence is via GORM `Firewall` rows.

### File path safety equivalence
- Both sides enforce **canonical, absolute, no traversal**: Beacon `hostfiles.go:22` `cleaned != normalized || Contains(\\ )` vs Forge `handlers_files.go:556` same predicate; both deny `/` and daemon data dir (`hostfiles.go:58` vs Forge proxy validates before dispatch). Beacon additionally collapses allowlist: `SetHostFileAllowlist` (`hostfiles.go:92`) validates each root.

### Monitoring pipeline completeness
- 1Panel `monitor.go:26` `monitorService.LoadMonitorData` returns gzipped time-series; `host.go` etc. are for remote hosts, not local telemetry. Forge `handlers_host.go:59` `handleHostInfo` slices uptime from `s.started` (`:65` `time.Since(s.started).Seconds()`), not from `/proc/uptime` — so after a Beacon restart uptime resets (vs system uptime). This is intentional (daemon uptime) but diverges from 1Panel's expectation.

## 4. Logic Findings (≥3 required)

### LF-01 — Firewall source restriction is secure-by-default but breaks 1Panel's "open to internet" UX (behavioral regression if 1Panel configs are migrated)

- **Location:** `beacon/internal/server/handlers_firewall.go:129` `validateFirewallSource` → `:163` `safeFirewallSourceIP` (`IsGlobalUnicast && !IsPrivate && !IsLoopback && !IsLinkLocalUnicast`), error at `:132` `"unrestricted rules are not allowed"`; `firewall.go` rule construction at `:347` always emits `-s <sourceIp>`.
- **1Panel expectation:** Port rules in `firewall.go:90` `OperatePortRule` accept a plain port+strategy; empty `SrcIP` implies any-source. Migration scripts or panel UI that create an "open 25565/tcp to all" rule will **fail validation** in Forge with 400.
- **Impact:** Medium — security gain, but migration tooling must rewrite `allow 25565/tcp from 0.0.0.0/0` as two explicit CIDR rules or document the policy. Beacon's `reconcile` (`:388` writes `-s %s`) has no path for a source-less ACCEPT, so data-model alignment is enforced end-to-end.
- **Recommendation:** Keep restriction, but add explicit Forge docs + if needed a gated `allowAnySource` flag behind `infra_admin` that emits `-s 0.0.0.0/0` when reviewed.

### LF-02 — Host file allowlist/denylist divergence plus upload body handling double-read risk

- **Location:** Beacon `hostfiles.go:51` `resolveHostPath` — with **empty allowlist** it blocks `"/"` + `hostFileDenylistPrefixes` (`:36`: `/etc,/proc,/sys,/dev,/boot,/usr,/bin,…,/var/run,/run`). Forge API `handlers_files.go:386` `hostFilesUpload` reads `c.Request().Body()` eagerly into `rawBody` (`:402`) then proxies with `bytes.NewReader(rawBody)` while also checking `ContentType` and consuming `r.Body` again on the beacon side.
- **Finding 1 — Conservative denylist blocks legitimate operator roots:** With no `DAEMON_HOST_FILES_ALLOWLIST`, valid operator paths under `/opt/forge` or `/srv` may be incorrectly denied if they fall under denylisted parents (`/usr` is too broad if custom tooling lives under `/usr/local/forge`). 1Panel's `file.go:583` `WgetFile` / `400` `UploadFiles` allow writes anywhere the agent uid can write, with only `ShouldDenySensitiveFileRead` (file.go:650) for reads. Forge is stricter — which is good — but default config must ship with explicit allowlisted roots or operators see "protected system location" errors.
- **Finding 2 — Body double-buffer is size-unsafe:** Forge's `hostFilesUpload` (`handlers_files.go:402`–`408`) buffers the entire body into memory without an explicit cap beyond Fiber's default, then forwards with `ContentLength = len(rawBody)`. Beacon caps at `hostUploadLimit = 100 MiB` (`hostfiles.go:457`). A 400 MiB multipart from an admin will OOM the Forge API before the beacon limit applies. 1Panel's upload path (`file.go:400` `UploadFiles`) streams via `c.MultipartForm()` and `c.SaveUploadedFile` with per-file handling and `buserr.MultiErr` aggregation — no single full-body alloc.
- **Recommendation:** Enforce `c.Request().Body() ` via `io.LimitReader` before buffering (or stream to beacon with chunked encoding), and ship a default `DAEMON_HOST_FILES_ALLOWLIST=/srv/game-panel,/opt/forge,/tmp` example.

### LF-03 — Cronjob retry & trigger semantics create unbounded execution parallelism; validation gap between FE and BE

- **Locations:** `forge/api/internal/services/cronjob/service.go:158` retry loop `for i:=0; i< job.RetryCount; i++ { time.Sleep(5*(i+1)s); CreateCronJobExecution; run/dispatch; Complete }` inside `executeJob` (which itself runs **directly on the cron goroutine** at `:90` `cron.AddFunc(... s.executeJob...)` with `context.Background()`); `handlers_cronjob.go:22` `parts[0]=="*" && parts[1]=="*"` guard; `forge/web/app/admin/cron-jobs/page.tsx:39` `parseCronExpression` only checks 5-field count, not semantics.
- **Findings:**
  1. **In-goroutine sleep blocks scheduler:** `executeJob` sleeps inside the cron goroutine (`:161` `time.Sleep`), blocking other jobs that share the same `cron.Cron` instance until retries finish (retry 10 × avg 27s = 4.5 min stall). 1Panel's `cronjobService` analogous code likely offloads to a worker pool (not inspected here, but standard). Forge should spawn retries in a separate goroutine or use a jittered backoff queue.
  2. **TriggerNow fires duplicate parallel executions:** `TriggerNow` (`:263`) creates one execution record, then **go-routines** `executeJob` which itself creates *another* execution at `:124` (`CreateCronJobExecution`). The caller-visible execution never completes; a second one runs. If the triggerCaller polls by returned ID, it sees a hung `pending` row. 1Panel's `HandleOnce` (`cronjob.go:348`) returns only success, not an ID, avoiding the confusion.
  3. **FE/BE validation mismatch:** FE `parseCronExpression` (`cron-jobs/page.tsx:39`) permits `* * * * *` (every minute) while BE `validateCronSchedule` rejects `parts[0]=="*" && parts[1]=="*"` (every-minute) with 422. Operators see a silent 422 after a client-allowed submit, not inline feedback.
- **Severity:** Medium.

### LF-04 — Monitoring synthetic-data fallback hides real infra gaps; uptime/metrics semantics shift

- **Locations:** `forge/web/app/admin/monitoring/page.tsx:62` `isSynthetic` (`every cpuLoad1m==0 && networkRx==0`), `:117` warning "allocated capacity (not live OS usage)"; `beacon/internal/server/handlers_host.go:65` `Uptime: time.Since(s.started).Seconds()`; `beacon/internal/server/sysinfo_linux.go:45` `cpuModel` reads `/proc/cpuinfo`; `beacon/internal/metrics/metrics.go:14` `dynamicPathSegment` regex.
- **Finding:** Beacon `handleHostInfo` reports **daemon uptime**, not host uptime (`:65`), while UI labels it "Uptime" without qualification (host page `host/page.tsx:98` `fmtUptime(data.uptimeSeconds)`). After a beacon restart, operators mis-diagnose a host reboot. Likewise `mem`/`disk` are computed via `unix.Statfs`+`unix.Sysinfo` fresh per request (correct), but CPU load/network series fed to monitoring charts are PLACEHOLDER zeros until beacon ships live collectors — the `isSynthetic` guard is a UI band-aid, not a fix. 1Panel's `MonitorBase` (`model/monitor.go:3`) reports all four load averages plus `TopCPU`, `Mem`, etc. live.
- **Secondary:** `handlers_metrics.go:77` builds `http_requests_total` keys as `"%s_%s_%d"` with `strings.SplitN(key,"_",3)` at `:131` — paths containing underscores (e.g., `/api/v1/game_servers_2`) would split incorrectly; 1Panel has no comparable cardinality logic.

### LF-05 — Snapshot vs backup retention semantic (AND vs OR) causes silent extra deletions

- **Location:** `forge/api/internal/services/backup/service.go:766` `keep[backup.Name] = backup.IsLocked || (withinCount && withinAge)` inside `EnforceRetentionPolicy`; `model/cronjob.go:39` `RetainCopies`; `model/snapshot.go:29` `IgnoreFiles`.
- **Finding:** Policy enforcement requires **both** within-count **and** within-age to keep a backup. Standard expectation is OR (keep N newest regardless of age, and also keep age-window regardless of count). With `MaxBackups=5, RetentionDays=7`, a 6th backup 3 days old that is outside count but inside age gets deleted — operators lose a valid point-in-time. 1Panel's `RetainCopies` on cron jobs is simpler (count-only). The backup `CleanupExpiredBackups` (`:689`) already has a two-phase pass (policies + global `ListExpiredBackups`) which could double-delete if a backup matches both predicates (harmless but logs duplicate work).
