## 1. Executive Summary

1Panel is a **single-host appliance panel**: it *is* the host truth (daemon JSON, ufw/firewalld + raw iptables chains, sshd config, fail2ban jails, FTP daemon, multi-host SSH inventory, system snapshots, 1.4k-line file manager with compress/wget/chunk/share/AI-search, and live `gopsutil` streaming). Forge is a **fleet orchestrator**: Beacon agents expose host telemetry and host-file/firewall/Docker facets over a signed, admin-scoped daemon API, while Forge API is a **proxy/routing layer** (`resolveNodeHostTarget` → `Daemon.GetHost*` → `mapDaemonError:504/502`) with node affinity and heartbeat-gated terminal access.

**Three headline verdicts for this seam:**

1. **REJECT, not MISSING, dominates host-tool sprawl.** SSH daemon tuning, fail2ban, FTP, `daemon.json` live-edit, system-image snapshots, GPU/device tooling, and multi-host SSH inventory are *intentionally absent* in Forge (immutable infra + MTLS + external provisioning assumption). Documenting them as MISSING overstates gap count and would prescribe rebuilding a control-plane-host-tool sprawl the report explicitly warns against (`FINAL §22` “host-tool sprawl … NOT to copy”).
2. **Forge is strictly STRONGER on confinement.** 1Panel’s `file.go` can write anywhere the agent uid can; Forge’s `hostfiles.go` allowlist-vs-denylist + `secure_files.go`/`rootfs` openat2 `RESOLVE_BENEATH|RESOLVE_NO_MAGICLINKS|RESOLVE_NO_SYMLINKS` + `AtomicWrite` + quarantine/merge staging is a kernel-enforced boundary absent in Wings and 1Panel. The tradeoff is the opposite direction: where 1Panel is permissive-by-default, Forge is deny-by-default and must ship explicit allowlisted roots.
3. **Remaining gaps cluster in *fidelity*, not breadth:** file manager richness, live process metrics, single-disk vs full partition table, network interface completeness, firewall policy UX, cron dispatch wiring, and monitoring synthetic-zero fallback (`monitoring/page.tsx:50 isSynthetic`) all require activation/polish rather than net-new subsystems. Four load-bearing logic findings are re-confirmed with host-admin impact (§6).

## 6. Logic Findings — Host-Admin Specific (≥4 required; 5 filed)

### LF-01 — Host file upload buffering — unbounded Forge API alloc before Beacon `100 MiB` cap (DoS via OOM)

- **Locations:** `forge/api/internal/http/handlers_files.go:386 hostFilesUpload` `388 target,err:=resolveNode` `392 destPath validation` `396 ContentType check` `402 rawBody:=c.Request().Body()` `403 bytes.NewReader(rawBody)` `408 ContentLength=int64(len(rawBody))` `410 SignedHeaders(... rawBody)` `420 HTTPClient().Do` — vs **Beacon** `beacon/internal/server/hostfiles.go:457 const hostUploadLimit=100*1024*1024` `458 http.MaxBytesReader(w,r.Body,hostUploadLimit)` `488 hostAtomicWrite(...hostUploadLimit)` with `LimitReader limit+1` guard. Prior audit LF-02 (§2 Finding 2) already raised; this audit reconfirms with exact lines.
- **Logic gap:** Forge buffers the *entire* request body into `rawBody` slice without an `io.LimitReader` or `Fiber BodyLimit` guard beyond Fiber’s default (which is typically ~former `BodyLimit` not enforced here). A 400 MiB `multipart/form-data` from an admin will OOM the Forge API container **before** the beacon’s `MaxBytesReader` ever runs. 1Panel’s path `file.go:400 UploadFiles` streams via `c.MultipartForm()` + `c.SaveUploadedFile` per-file without single full-body alloc (`buserr.MultiErr` aggregation).
- **Host-admin impact:** Single-host admins expect “upload a big backup/tar to host”; Forge’s proxy becomes the weakest link in the fleet — one upload can degrade the control plane for all nodes.
- **Evidence of limit asymmetry:** Beacon enforces `hostUploadLimit 100 MiB` (`hostfiles.go:457`) while Forge’s handler has no `len(rawBody)` pre-check before alloc; `hostAtomicWrite :124 Limit+1` is reached only after full buffering.
- **Severity:** **P1** — resource exhaustion via authenticated admin path.
- **Recommendation:** (a) In `hostFilesUpload` enforce `io.LimitReader` **before** buffering (or better: stream via `io.Pipe` chunked encoding to beacon without `rawBody` alloc; compute `SignedHeaders` over stream or sign canonical metadata only). (b) Set `Fiber BodyLimit` or explicit `if c.Request().Header.ContentLength() > 100*1024*1024+ slack` early 413. (c) Add regression test: 101 MiB multipart should 413 at Forge API layer without beacon call. (d) Align with `secure_files.go:27 defaultMaxUploadBytes 2 GiB` per-server vs host `100 MiB` — document divergence.

### LF-02 — Cron `TriggerNow` duplicate execution rows (caller polls hung `pending` row)

- **Locations:** `forge/api/internal/services/cronjob/service.go:263 TriggerNow` `268 execution,err:=CreateCronJobExecution(ctx,jobID)` `273 go func(){ 281 s.executeJob(context.Background(),jobID) }` `284 return execution,nil` vs `117 executeJob` `124 execution,err:=CreateCronJobExecution(ctx,jobID)` `154 CompleteCronJobExecution` (+ retry loop `163 retryExec:=CreateCronJobExecution`). **Handler** `forge/api/internal/http/handlers_cronjob.go:196 POST /cron-jobs/:id/execute → 202 execution,err:=cronJobService.TriggerNow`.
- **Logic gap:** `TriggerNow` creates one `CronJobExecution` row and returns its ID to the caller, then async-spawns `executeJob` which **creates a second** execution row and completes *that* one. The caller-visible execution row stays `pending/created` forever (never completed), while a shadow execution runs. If the FE polls `GET /cron-jobs/:id/executions` filtered by `execution.id == returned.id`, it observes a hung row. Prior audit `phase-06/subagent-04 LF-03 Finding 2` flagged the same dupe; this re-verification confirms it persists at `service.go:268 vs :124`.
- **1Panel comparison:** `reference/app-platforms/1panel/agent/app/api/v2/cronjob.go:348 HandleOnce` returns only `Success` (no ID), avoiding the confusion — though it sacrifices traceability. Forge wants ID traceability but double-creates.
- **Severity:** **P2** — functional correctness; confused operators + poll loops; retry loop compounds confusion (each retry creates yet another row).
- **Recommendation:** Change `TriggerNow` to either (i) create the outer row and pass its ID into `executeJobWithExecution(ctx, jobID, executionID)` (no second create), or (ii) not create outer row and have `TriggerNow` synchronously return the *inner* execution’s ID after `Create` (requires channel/sync). Add test: `TriggerNow` should yield exactly 1 new row until completion. Fix is ~5 lines.

### LF-03 — Monitoring synthetic-zero fallback hides infra gaps; “Uptime” and “Processes Sort” lie (host page)

## 10. CapRover / Dokku / Uncloud Host Patterns — Why They Do Not Prescribe Forge Host Admin

**CapRover:** One host, one `ServiceManager` per node, one `captain-definition` (`ICaptainDefinition.ts:1`) schema-versioned exactly-one-of image/direct/DockerfileLines (`ImageMaker.ts:416-427`) + fallback to bare `Dockerfile`. Host reality is **swarm service** state (`createServiceOnNodeId/updateService` + `reloadLoadBalancer`). No host inventory, no firewall, no file manager — host is the swarm. Forge should not mimic this: fleet’s nodes are reservations + heartbeat, not swarm nodes, but CapRover’s “definition → Dockerfile tar → build → retag → push” pipeline is a useful minimal build model already superseded by Forge’s honest `build/service.go:140 Detect Dockerfile else nixpacks`.

**Dokku:** Filesystem truth (`$DOKKU_ROOT/<app>` dir + `VHOST/ENV/DOKKU_SCALE/VHOST` files) + shell `plugn trigger <name>` bus (`common/plugn.go:42`) with ~60 discrete plugins (`plugins/{ps,checks,apps,proxy,network}`) + `scheduler-docker-local` (single-host `docker run` with `ps:scale` `DOKKU_SCALE`). Host admin is `dokku` CLI on the host, not a panel. Forge’s panel cannot adopt “filesystem is DB” — but Dokku’s `plugn` trigger pattern does illuminate why `handlers_cronjob.go` / `handlers_firewall.go` style lightweight proxy + beacon execute is the right seam (panel triggers, daemon executes) — same split as `plugn trigger scheduler-deploy`.

**Uncloud:** No control plane by design (`AGENTS.md:31 “Decentralized, no control plane”`), CRDT `Corrosion` gossip (`corrosion/client.go:1`) + membership `ALIVE/SUSPECT/DOWN` (`cluster.go:209-238` local override UP), IPAM `10.210.0.0/16 /24` (`IPAM AllocateSubnetLen :113-162`) with **concurrent allocation overlap risk** (`:150-159` no distributed lock + TODO `:174`), fat-client `RunService → InspectClusterState → VolumeScheduler → Deployment.Run` fan-out (`pkg/client/service.go:21-86`), `dns.Server` with `nearest.` locality sort (`dns/server.go:294-326`). Forge’s central Postgres + `heartbeatmonitor` FSM is deliberately the opposite choice at fleet scale — `FINAL §22` correctly says “Uncloud CRDT-no-quorum (trades consistency Forge needs)” is **NOT to copy**. Host mesh comparison therefore validates Forge’s central placement, not gaps.
