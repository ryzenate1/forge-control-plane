### 6. Renewal Mechanics (key reuse, account binding)

| | |
|---|---|
| **REFERENCE** | traefik:`renewCertificates` passes existing private key + cert into `client.Certificate.Renew` (provider.go:936–950) using the resolver's own persisted account; caddy:certmagic reuses storage-backed account per issuer key |
| **FORGE** | `acme/service.go:renewOnce` (service.go:492–546): parses stored key, resolves account via `getAccountKeyForRenew(ctx, caURL)` (service.go:336) which returns the **first** account matching the CA URL (findAccountByCA service.go:612–638), falling back to creating `admin@localhost` |
| **STATUS** | ⚠️ Implemented with correctness risks |
| **GAP** | Account selection ignores which account/email actually issued the cert — with two accounts on the same CA (different emails), renewals can flip accounts (LE ties orders to accounts; still works because cert renewal authorizes via new order, but audit trail and future revocation break). No persistence of registration URI (see #1). |
| **FORGE LOGIC** | `renewOnce` re-registers each cycle (service.go:530) and calls `client.Certificate.Renew(..., true /*bundle*/, false, "")` (service.go:536–540) — the trailing `""` discards preferred-chain, and `false` disables key reuse... actually lego's signature here means "bundle=true, privateKey reused implicitly"? In lego v4 `Renew(certRes, bundle, mustStaple, preferredChain)` — the cert resource carries `PrivateKey`, so the old key is reused, contradicting best practice (Caddy generates a NEW key per renewal by default, automation.go:144–151 rationale: mitigate pinning/key-compromise). |
| **FINDING** | **Forge reuses leaf private keys across renewals forever** (stored `private_key` passed back into Renew). Caddy explicitly treats this as an anti-pattern (automation.go:146–150). |
| **RECOMMENDATION** | Store the issuing account ID (FK) on `certificates`; on renewal generate a fresh CSR/key (or pass empty PrivateKey to lego Renew) and persist the new key; persist preferred chain. |
| **SEVERITY** | High |

## Logic Findings Summary (≥3 required)

### LF-1 — Dead HTTP-01 solver (Critical)
`acme.Service.HTTPSolver()` (service.go:157–159) returns a fully-implemented challenger (service.go:52–92) that is mounted nowhere: `grep -r HTTPSolver forge/api` yields only the definition. Every HTTP-01 `IssueCertificate` call therefore stalls in lego's validation poll until timeout, then burns retry budget (service.go:444–462). Since `ChallengeTypeHTTP01` is the **default** challenge type (service.go:203–205), the most common API invocation is guaranteed to fail. Fix: mount the handler on :80 (or reverse-proxy the path from the edge).

### LF-2 — Certificates never leave the database (Critical)
The gateway abstraction defines `SetCertificate/RemoveCertificate` (gateway_adapter.go:49; caddy_proxy.go:83; traefik_proxy.go:373) but has **no callers** anywhere in the repo (verified by grep). Renewal updates only Postgres (service.go:355–363); `runAutoRenewal` (service.go:420–438) has no post-renew hook; `domainsenv` records `CertID` (domainsenv/service.go:214) with no consumer. Contrast: traefik feeds renewed certs into its dynamic-config channel (provider.go:800–802) and npm reloads nginx post-renew (certificate.js:155–186). Result: even successful issuance produces no TLS on any proxy unless the separate embedded-Caddy `ProvisionLetsEncrypt` path (caddy_tls.go:34) is used exclusively.

### LF-3 — Permanent private-key reuse on renewal (High)
`renewOnce` reconstructs `certificate.Resource` with the **stored** `PrivateKey` DER (service.go:536–540), so every renewal re-uses the original leaf key indefinitely. Caddy documents why this is undesirable — new key per cert mitigates pinning and shrinks compromise scope (automation.go:144–151, `reuse_private_keys` opt-in only). Additionally the account used is "first account matching CA URL" (service.go:612–638), decoupled from the issuing identity.

### LF-4 — Secret-tier inconsistency for DNS credentials (High)
Migration 157 encrypted `acme_accounts.private_key_encrypted`; cert keys were sealed from day one (094 + store_certificates.go:86). Yet `certificates.dns_credentials` (migration 134) and `dns_provider_accounts.credentials` (migration 135) remain plaintext JSONB containing cloud DNS API tokens — credentials that can hijack the entire zone. NPM at least writes its credential file 0600 (certificate.js:833). Same `encryptSecret/AAD` machinery applies unchanged.

### LF-5 — Auto-renewal goroutine panic kills the loop permanently (Medium)
In `StartAutoRenewal` the `defer recover()` (service.go:390–396) wraps the goroutine *outside* the `for` loop — any panic in `runAutoRenewal` ends the scheduler silently for process lifetime. The durable `JobCertRenewal` fallback (main.go:1178–1192) bounds the blast radius, but the primary path should recover per-tick.

### LF-6 — `admin@localhost` default contact (High)
Default email synthesized in `IssueCertificate` (service.go:198) and renewal fallback (service.go:507, 609) is not a registrable contact at any public ACME CA; issuance via the no-email path fails opaquely. NPM hard-blocks without a real user email (certificate.js:145–150).
