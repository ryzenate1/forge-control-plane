## 3. Findings (≥3) — file:line citable

### F-01 — [MEDIUM] GH-11 explicit `protocol+containerPort` fix verified, but legacy `mappings map[string][]int` fallback still silently drops protocol (dual tcp/udp exposure + containerPort loss)

- **Evidence:** `forge/api/internal/services/clustermanager/service.go:698` builds `mappings := map[string][]int{}` only from `allocation.Port` ignoring `allocation.Protocol` and `allocation.ContainerPort`; `699` `allocations["mappings"]=mappings` shipped in `ServerConfiguration.Allocations` alongside richer `allocations["ports"]`. Any consumer using `mappings` (documented Wings compat) will see `mappings["10.0.0.1"]=[25565]` regardless of `tcp` vs `udp`, so a `udp`-only `8211` (e.g., `valheim`) will be inferred as both `tcp`+`udp` if wings `Bindings():53` style logic applied (`allocations.go:53` `out[tcp]=binding; out[udp]=binding`). Beacon itself uses explicit `Ports[]` correctly (`docker.go:892` `nat.Port(containerPort/protocol)`), so live workloads are unaffected today — but the compat field is semantically wrong.
- **Secondary:** `store_allocations.go:182` duplicate error still says `allocation with ip %q and port %d already exists on this node` without `protocol` in message, despite constraint `090_allocation_transport.sql:14` `UNIQUE (node_id, ip, port, protocol)` allowing same `ip:port` with different protocols. Admin sees confusing "already exists" when inserting `udp` then `tcp` with same `ip:port` but different protocol would actually succeed; the error template is stale (not security but confusing).
- **Recommendation:** Keep explicit `Ports[]` canonical, deprecate `mappings` in `runtimeConfiguration:698` (emit nil or per-protocol struct) or fix to `map[string]map[string][]int` (ip→protocol→ports) and include `containerPort`. Update `store_allocations.go:183` error to include `protocol`.
- **Reconciles:** `FINAL_PARITY GH-11` claimed COMPLETE+ (richer) — true for explicit path, but residual `mappings` not flagged there is still wrong; `phase-02 C08` note "protocol vs Wings dual" is correct; `subagent-01 C-11` LF already flagged `HostKey` protocol distinction but not `mappings`. This reverification confirms `phases-02/subagent-02 C08` + `final-parity subagent-01 C-11` and downgrades legacy compat to BROKEN.

### F-02 — [MEDIUM] CPU `cpu_shares` vs `CPUPercent` (percent) conflation persists; beacon always pins `CPUShares=1024` even when `CPUPercent=0` (unlimited), and units disagree (threads*100 vs 0..100000)

- **Evidence:** Wings semantics `settings.go:52` `CpuLimit percent 0..threads*100`; `settings.go:124` `if CpuLimit>0 {CPUQuota=CpuLimit*1000; CPUShares=1024}` — unlimited (`CpuLimit==0`) sends **no** CPU constraints (shares not set). Forge panel `handlers_servers.go:819-820` `cpuShares default 1024` unconditionally alongside `cpuLimit default 0 (unlimited)`. `store_servers.go:209` allows `CPUShares 1..?` with `CPULimit 0`. `clustermanager/service.go:672` forwards both `CPUShares/CPULimit` → `gpruntime` → `daemon/client.go:401` `CPUShares/CPUPercent` → `beacon/runtime/runtime.go:65` `CPUShares/CPUPercent`. `beacon/internal/runtime/docker.go:802` `buildResources` always sets `CPUShares:req.CPUShares` regardless of `CPUPercent==0`, vs wings conditional. `docker.go:924` validates `CPUPercent 0..100000` (centi-percent, 100x wings percent), while `store_servers.go:209`/`handlers_servers.go:827` do not cap `CPULimit` (allow any `≥0`). Unlimited containers therefore get `CPUShares=1024` weight throttling in Forge but not in Wings — divergent.
- **Impact:** Performance regression (unlimited servers artificially weighted), or conversely an admin setting `CPULimit=200` (2 cores, wings-style) vs `CPUPercent=200` means `quota=period*200/100=200000` → 200% (correct) but a panel value `20000` (centi) would be 200x too high. Units not documented; `shared-types/api.ts:98` `cpuShares/cpuLimit` vs `97` `cpu`/396 `cpu?` naming confuses. `beacon/internal/runtime/override_test` would not catch cross-layer mismatch.
- **Recommendation (no code change per instructions — document):** Align semantics: either (a) treat `CPULimit` as centi-percent 0..100000 and fix panel validation to cap same as `docker.go:924`, or (b) treat as wings percent 0..threads*100 and make `buildResources` conditional `if CPUPercent>0 {CPUShares=...}` matching `settings.go:124`. Document mapping in `daemon/client.go:400` comment and `shared-types/api.ts:98`. Currently BROKEN divergence.

### F-03 — [HIGH — re-confirms GH-19/SE-04] Panel `validateMountPath` allowlist too narrow; only `{/etc/forge,/var/lib/forge/volumes}` source + `{/ ,/home/container}` target blocked — leaves host breakout surface at API
