## 3. Logic Findings — Host Seam (5 filed; 2 P1, 3 P2)

### LF-01 — [P1] Host-file upload buffering in Forge API is unbounded before beacon's `100 MiB` cap — OOM via authenticated admin path

- **Locations:** `forge/api/internal/http/handlers_files.go:386` `hostFilesUpload` `402` `rawBody := c.Request().Body()` `403` `bytes.NewReader(rawBody)` `408` `ContentLength = int64(len(rawBody))` `410` `SignedHeaders(..., rawBody)` `420` `HTTPClient().Do` — vs **Beacon** `beacon/internal/server/hostfiles.go:457` `const hostUploadLimit = 100*1024*1024` `458` `http.MaxBytesReader(w,r.Body,hostUploadLimit)` `488` `hostAtomicWrite(...hostUploadLimit)` with `LimitReader limit+1`.
- **Re-verification:** Prior `phase-06 LF-02` and `final-parity LF-01` both flagged; code is **unchanged** on this checkout — no `io.LimitReader` or `ContentLength` guard inserted at `handlers_files.go:402` before alloc. `validateHostFilePath:547` checks path shape but not size. `hostFilesWrite:313` (JSON `content` path) is bounded by `16 MiB` `secure_files.go:27` `maxFileWriteBytes` via `hostAtomicWrite`, but the multipart/octet upload path has no Forge-side cap. 1Panel `file.go:400` streams via `c.MultipartForm()` per-file without full-body alloc.
- **Impact:** Single 400 MiB multipart from an admin OOMs the Forge API pod (fleet control plane) before beacon's `MaxBytesReader` runs — cross-node DoS. Repeats prior P1 severity.
- **Recommendation:** Enforce `ContentLength`/ `BodyLimit` before buffering (413 if `> hostUploadLimit + slack`), or better stream via `io.Pipe` chunked to beacon and sign canonical metadata instead of `rawBody`. Add regression test: 101 MiB multipart → 413 at Forge without beacon call. Document `100 MiB` host vs `2 GiB` per-server `secure_files.go:28` `defaultMaxUploadBytes` divergence.

### LF-02 — [P2] `TriggerNow` creates duplicate execution rows — caller polls a permanently `pending` row

- **Locations:** `forge/api/internal/services/cronjob/service.go:263` `TriggerNow` `268` `execution,err:=CreateCronJobExecution(ctx,jobID)` `273` `go func(){ 281 s.executeJob(context.Background(),jobID) }` `284` `return execution,nil` vs `117` `executeJob` `124` `execution,err:=CreateCronJobExecution(ctx,jobID)` `154` `CompleteCronJobExecution`.
- **Re-verification:** Exact dupe persists from `phase-06 LF-03 finding 2` — re-confirmed at same lines. `handlers_cronjob.go:196` `POST /cron-jobs/:id/execute` returns the outer row; `225` `GET /cron-jobs/:id/executions` lists both. FE polling `execution.id == returned.id` observes hung `pending`. Retry loop `158` compounds: each retry creates yet another row (`163`), so `TriggerNow` with `RetryCount>0` can yield `2+N` rows for one manual trigger.
- **Impact:** Confused operators, hung poll loops, audit log inflation. 1Panel `cronjob.go:348` `HandleOnce` avoids ID entirely.
- **Recommendation:** Single-create: either pass outer `execution.ID` into `executeJobWithExecution(ctx, jobID, executionID)` (no second `Create`), or don't create outer row and return inner ID via channel after `Create`. Add test: `TriggerNow` → exactly 1 new row until completion. ~5-line fix.

### LF-03 — [P2] In-goroutine retry `Sleep` blocks the `cron.Cron` scheduler + FE/BE `* *` validation mismatch

- **Locations:** `forge/api/internal/services/cronjob/service.go:158` `for i:=0; i<job.RetryCount; i++ { 161 time.Sleep(5*(i+1)*time.Second); ... }` inside `executeJob` invoked at `90` `cron.AddFunc(... s.executeJob...)` with `context.Background()`. `forge/api/internal/http/handlers_cronjob.go:22` `parts[0]=="*" && parts[1]=="*"` 422 vs `forge/web/app/admin/cron-jobs/page.tsx:39` `parseCronExpression` (per prior audit — not re-opened this pass but claim re-verified via handler).
- **Re-verification:** Sleep blocks `cron.Cron`'s single job goroutine (default `cron` with no `WithChain` wrapper) — other jobs sharing the instance stall up to 4.5 min on `RetryCount=10`. Handler correctly rejects every-minute (`22`) at admission with 422; FE parser (per `phase-06`) only checks 5-field count, so operators get silent 422 after client-allowed submit, not inline feedback. Command length cap `82`/`156` `4096` is wired but not surfaced in FE validation either.
- **Recommendation:** Dispatch retries to a separate goroutine/queue with jittered backoff (or `time.After`), not inside the cron callback. Sync FE `parseCronExpression` to mirror `validateCronSchedule` `* *` reject and `cron.NewParser` error strings.
