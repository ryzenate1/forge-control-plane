`<div>` (no width frame) 4 · `AdminPage`/`ForgePage` (the documented canonical frame) **0** ·
`DashHeader` 2, both rendered **inside modals**, never as a page header · `ForgeDialog` 1 page (`compose-templates/page.tsx:298`, `:407`) vs
`Modal` 5 files (`deployments/page.tsx`, `compose/[id]/page.tsx`, `pipelines/page.tsx`,

**Brief correction the orchestrator needs:** the brief's premise "three files already import both
header systems (`deployments/page.tsx`, `pipelines/page.tsx`, `compose/*`)" is 2/3 right. Confirmed by
grep: `app/admin/compose/**` imports **only** `admin-ui` (`compose/page.tsx:10`,
`compose/new/page.tsx:8`, `compose/[id]/page.tsx:11`) — no compose file touches `dashboard-cards`.
The complete list of `dashboard-cards` consumers in the whole repo is
`app/admin/pipelines/page.tsx:44`, `app/admin/deployments/page.tsx:13`,
`app/admin/apps/[id]/page.tsx:23` (+ two out-of-scope files). So the Deploy slice has **two**
double-frame files, and in both the collision is a **modal**, which is worse than a stacked page
header — documented per page below. Also: `deployments/page.tsx` imports `SectionHeader`, not
`AdminPageLayout` (`:12`); it has no page frame at all, just `<div className="space-y-6">` (`:99`).

**Zero routes in this slice use the documented canonical frame** `AdminPage`
(`components/admin/admin-page.tsx`), so none of the registry-derived title/description/eyebrow/trail
guarantees apply anywhere in Deploy.

- **S1 · The two tabs are the same endpoint, presented as two different kinds of deployment.** `page.tsx:53` fetches `fetchJSON<ServerDeployment[]>("/admin/deployments")` and `page.tsx:59` fetches `fetchAllDeployments()`, which is `fetchJSON<AppDeployment[]>("/admin/deployments")` (`lib/api/apps.ts:443-445`). An operator reading "Server Deployments: 12 / App Deployments: 12" is reading the same 12 records twice. This is the single largest truth-in-UI defect in the slice.
- **S1 · The App tab renders `#undefined` for every row whose revision the API did not send.** `page.tsx:268` is `#{dep.revision}` with no guard, and `AppDeployment.revision` is declared "Optional/legacy fields some views still reference; may be absent from the API" (`lib/api/apps.ts:116-124`). `Trigger` (`:273-275`) and the modal's Source/Trigger rows (`:342-343`) render an **empty Pill** for the same reason. Empty chip = "measured as nothing", not "not reported" (AGENTS.md).
- **S1 · Status tone is derived twice, differently, on the same screen.** Table cells use `statusConfig` (`page.tsx:32-38`: `pending→yellow`, `in_progress→blue`, `completed→green`, `failed→red`, `rolled_back→neutral`) at `:224`; the count strip 40px above uses its own inline ternary at `:179` (`completed→green, failed→red, in_progress|running→blue, everything else→neutral`) — so in one screen `pending` is amber in the row and grey in the strip, and `rolled_back` is grey in both even though `lib/api/status.ts:86` and `:151` both classify it as `warn`. A rolled-back release — the state that most needs an operator's attention — is rendered as "Inactive grey" by three of the four renderers on this page.
- **S1 · App-tab statuses are absent from every central map.** `appStatuses` is `["pending","running","completed","failed","canceled"]` (`page.tsx:89`) and `lib/api/status.ts:54-92` has `canceled→neutral` and `running→pending` — but the *page's own* `statusConfig` (`:32-38`) has no `running` and no `canceled` key, so `statusConfig[dep.status] ?? statusConfig.pending` (`:204`, `:371`) silently re-labels a cancelled or running app deployment as **pending/amber** in the modal header and the modal's `InfoCard` status row (`:393`).
- **S1 · A request that failed is reported as "no deployments exist".** `page.tsx:184-187`: the ternary is `isLoading ? … : currentData.length === 0 ? <EmptyState title="No server deployments yet" message="Create a blue-green/rolling deployment…">`. `serverDeploymentsQuery.isError` and `appDeploymentsQuery.isError` are read nowhere in the file. Same defect in `history/page.tsx:89-92`, `[id]/page.tsx:68-74` (an error renders "Deployment not found." — the record is reported missing when its state is unknown) and `[id]/revisions/page.tsx:199-202`.
- **S1 · "Rollback to Previous" is an enabled button that silently does nothing.** `revisions/page.tsx:98-110`: `const activeIdx = revs.findIndex(...); if (activeIdx < revs.length - 1) { rollbackMutation.mutate(revs[activeIdx+1].id) }` — when the active revision is the last array element the handler returns with no toast, no error, no state change, and the button is only disabled while a mutation is in flight. It also *assumes* newest-first ordering while the timeline's own gate is positional in the opposite direction (`canRollback = !isActive && idx > 0`, `:208`).
- **S2 · The frame collision, as the operator experiences it.** Clicking **Details** on an App row opens `Modal` (which renders its own dialog title bar + description, `admin-ui.tsx:432-434` → `Dialog`) whose body *immediately* renders `DashHeader` (`page.tsx:326-338`), then `InfoCard` (`:339-351`).
