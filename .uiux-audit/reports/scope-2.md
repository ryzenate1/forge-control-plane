   - `AdminServers.tsx:178` → `SectionHeader` · `AdminNodes.tsx:75` → `SectionHeader` (+ `DashHeader` `:269` in a tab)

## Open questions for the orchestrator

1. **Which page is the reference?** The rubric names five, but they disagree with each other: `AdminOverview`/`AdminServers` = `SectionHeader`, `AdminNodes` = `DashHeader`, `AdminMonitoring`/`AdminActivityLog` = `FreshnessBadge`, `AdminServers` = none. And the documented canonical frame has zero consumers. I have assumed `admin-page.tsx` is the target and `AdminServers.tsx`'s *behaviour* (labelled selects, no-match-vs-no-data, `useConfirm`) is the target interaction grammar. Confirm — this decides roughly 20 findings.
2. **Is `?tab=` the sanctioned sub-navigation mechanism?** `apps/[id]` does it, `database-services/page.tsx:18` assumes it, Databases does not implement it. If yes, Databases is a bug; if no, the stub page must be deleted. Cannot decide unilaterally because it implies a routing convention across all 88 routes.
3. **Are Service Catalog and App Store one product?** Both claim "one-click" in the registry, both browse a template catalog, and catalog instances already surface inside `/admin/databases` rows. Merging, or drawing a bright line, is a product decision that changes four registry rows.
4. **Does `/admin/database-services` still need to exist as a route at all?** Its registry entry is deliberately absent (`admin-registry.ts:101`) and its alias mapping exists — the filesystem route is what makes it render. Deleting it is a one-file change I am not authorised to make.
5. **Should `game_server` remain an `AppType`?** It is filterable in the Applications list (`apps/page.tsx:55`) but not creatable (`apps/new/page.tsx:23-27`), and it is the same concept as the Game Servers primary. Either the Applications type list loses a member or the two primaries need a stated boundary.
6. **Apps' `mapApplication` type coercion** (`lib/api/apps.ts:372-373`) turns an unknown source type into `"image"`. Fixing it honestly (surface "unknown") is a data-layer change with UI consequences in three pages, so it should be scheduled with the tone/unknown work in item 3, not done ad hoc.
